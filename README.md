## Серверна архітектура додатку(оновлення)
Серверна архітектура побудована за принципом розподілу відповідальності. Основний файл сервера `server.js` виконує роль точки входу, де ініціалізуються ключові модулі, налаштовуються проміжні обробники та запускається прослуховування мережевого порту.
Логічна структура додатку складається з кількох основних шарів. По-перше, шар конфігурації, що відповідає за підключення до бази даних MySQL та завантаження змінних середовища з файлу `.env`. По-друге, шар маршрутизації, що визначає структуру API-ендпоінтів. Маршрути розділені за логічними блоками -  `/api/recipes` для роботи з контентом, `/api/auth` для керування користувачами та `/api/favorites` для персоналізації. І наостанок, шар контролерів, що містить безпосередню бізнес-логіку програми. Контролери приймають дані від маршрутизатора, виконують необхідні обчислення та формують HTTP-відповідь.
Також, важливою частиною архітектури є використання Middleware-функцій. Це проміжна логіка, яка виконується між отриманням запиту сервером і поверненням відповіді клієнту. Дана логіка включає в себе - JSON парсер для автоматичного перетворення вхідних даних у зручні об’єкти, `cors` модуль для регулювання доступу до API з різних доменів, і спеціальний модуль для захисту адмін-панелі. Він перевіряє наявність та валідність JWT токена в заголовках запиту, відхиляючи неавторизовані спроби зміни даних.
Взаємодія з базою даних MySQL на серверному рівні реалізована через драйвер `mysql2`. Механізм пулу з’єднань дозволяє не створювати нове з'єднання для кожного окремого запиту користувача, а повторно використовувати існуючі, що суттєво знижує навантаження на систему.

### Обробка запитів та взаємодії з базою даних на сервері
У даному проєкті, процес обробки клієнтських API-запитів тісно інтегрований з механізмами доступу до бази даних. Коли клієнтська частина ініціює мережеве звернення, першим етапом на сервері є маршрутизація. Фреймворк Express.js перехоплює HTTP-запит та, опираючись на вказаний URL-шлях і тип методу, спрямовує його до відповідної функції-контролера.
	Критично важливим аспектом реалізації є використання параметризованих запитів при формуванні SQL команд. Замість прямого підставлення даних, отриманих від користувача, безпосередньо в рядок запиту, сервер використовує плейсхолдери. Такий підхід гарантує високий рівень безпеки, тому що драйвер бази даних автоматично екранує всі вхідні параметри, що унеможливлює проведення атак типу SQL injection і захищає систему від несанкціонованих маніпуляцій.
	Звернімо увагу, обробка запитів на отримання інформації переважно передбачає виконання операторів `SELECT`. Наприклад, для детального відображення сторінки конкретного рецепта сервер не обмежується зверненням тільки до головної таблиці рецептів. Контролер використовує оператори об'єднання `JOIN` для одночасного вилучення пов'язаних даних з довідника інгредієнтів та таблиці пропорцій.
	У випадку обробки запитів на модифікацію даних, алгоритм дещо ускладнюється. Контролер спочатку парсить та валідує інформацію, передану в тілі запиту. Переконавшись у коректності даних, сервер ініціює виконання команд `INSERT`, `UPDATE` або `DELETE`. Завершальним етапом циклу обробки є формування HTTP-відповіді. Якщо транзакція пройшла успішно, сервер повертає код `200` або `201`. У разі виникнення конфліктів або внутрішніх збоїв бази даних, блок обробки виключень перехоплює помилку та повертає відповідний код клієнту.

### Тестування та налаштування веб додатку на сервері
авершальним етапом розробки є його налаштування у середовищі виконання та повноцінне тестування. Процес налаштування серверної частини розпочинається з конфігурації змінних оточення. Для забезпечення високого рівня безпеки та уникнення витоку конфіденційної інформації, усі критичні параметри винесено у спеціальний прихований файл конфігурації `.env`. Серверна частина зчитує ці налаштування під час ініціалізації за допомогою модуля dotenv. Такий підхід відповідає сучасним стандартам безпеки розробки та дозволяє легко адаптувати систему до різних середовищ.
	На додачу до всього вищезгаданого, наступним етапом є комплексне тестування всієї системи у зв'язці з клієнтським веб-додатком безпосередньо у браузері. Перевірялася швидкість рендерингу карток десертів та коректність роботи асинхронних функцій під час додавання рецептів до списку закладок. Окремо варто зазначити, про тестування ключової бізнес-логіки проєкту - математичного алгоритму калькулятора перерахунку пропорцій інгредієнтів. Тестування цього модуля відбувалося шляхом введення як типових, так і нестандартних значень діаметрів форм, щоб переконатися у відсутності математичних похибок та миттєвому оновленні` DOM-дерева` без перезавантаження сторінки.

## Інтеграція сторонніх сервісів в систему
В сучасній розробці прийнято делегувати вузьконаправлені задачі стороннім сервісам. В даному випадку інтегрованими сторонніми сервісами є низка зовнішніх компонентів для Node.js, бібліотеки Google Fonts та хмарний сервіс EmailJS.
	З метою забезпечення безпеки персональних даних користувачів, було прийнято рішення не зберігати паролі у відкритому вигляді. Для цього в систему інтегровано криптографічний модуль bcrypt. Перед збереженням у базу даних MySQL пароль проходить процедуру хешування з використанням криптографічної солі. Вона являє собою дані, які застосовуються в процесі хешування для запобігання можливості розгадати оригінальне введення за допомогою пошуку результату хешування в списку заздалегідь обчислених пар введення-хеш[8].
	Для реалізації механізму авторизації без збереження стану було інтегровано стандарт JSON Web Token через сторонній пакет jsonwebtoken. Після успішної перевірки облікових даних сервер генерує унікальний зашифрований токен, який клієнтський додаток використовує для доступу до захищених маршрутів. Він автоматично перевіряє цілісність та термін дії токена при кожному запиті.
	Оскільки клієнтська та серверна частини можуть знаходитися на різних доменах або портах, було інтегровано проміжне програмне забезпечення cors. Цей модуль налаштовано таким чином, щоб дозволяти обмін даними лише з довіреними адресами клієнтського додатка, що захищає сервер від несанкціонованих міжсайтових запитів.
	Додатково варто згадати про інтеграцію сервісів для покращення типографіки сайту.  Це є важливою складовою будь-якого інтерфейсу, що безпосередньо впливає на читабельність тексту та загальне візуальне сприйняття продукту. Тож замість стандартних системних шрифтів було інтегровано сервіс Google Fonts. Підключення шрифтів реалізовано за допомогою мережі доставки контенту. У секції <head> HTML-документів додано відповідні теги <link>, що дозволяють браузеру користувача завантажити необхідні стилі шрифтів безпосередньо із серверів Google. Для додатку з рецептами рецептів було обрано, інтегрувати апетитні, солодкі шрифти Chewy та Cookie

## Розміщення та стилізація елементів інтерфейсу
На основі попередньо спроектованих структурних замальовок та затвердженої кольорової гами було реалізовано клієнтську частину веб-додатка. Для розміщення та стилізації елементів інтерфейсу використовувалися технології HTML5 та CSS3. Усі визначені кольори були підключені за допомогою глобальних CSS-змінних :root, що забезпечило єдність стилю та легкість його підтримки на всіх сторінках. 
Цікавою особливістю розробленого інтерфейсу є імплементація елементів сторітелінгу та легкої гейміфікації через використання детективної тематики. Концепція кулінарного розслідування інтегрована в логіку взаємодії користувача з веб-сайтом. Таке нестандартне концептуальне рішення вигідно відрізняє розроблений веб-застосунок від типових сухих каталогів рецептів, роблячи досвід використання більш захопливим та інтерактивним.
Математична основа калькулятора базується на принципі геометричної подібності. Оскільки більшість десертів мають форму циліндра, об’єм інгредієнтів прямо пропорційний площі основи форми
	У програмній частині цей коефіцієнт перемножується на базову кількість кожного інгредієнта, а результат округлюється до цілого числа для зручності користувача.
Поряд з тим, основною сторінкою додатка є каталог рецептів. Для виведення карток десертів у вигляді зручної сітки було застосовано CSS Grid. Це дозволило створити адаптивний макет, який автоматично підлаштовує кількість колонок залежно від ширини екрана користувача.

Для акцентування уваги на можливості зміни діаметра форми, поле введення та кнопка перерахунку виділені контрастним полуничним кольором. Використання напівпрозорого фону підкладки під час відкриття модального вікна дозволяє сфокусувати користувача виключно на поточному рецепті. 
Окрім функцій перерахунку, модальне вікно рецепта містить важливий елемент персоналізації - кнопку додавання у «Закладки». Кнопка розміщена у верхній частині вікна поруч із назвою десерту, що забезпечує її швидку доступність.

З метою забезпечення коректного відображення на мобільних пристроях, інтерфейс розроблявся за принципом адаптивного дизайну (англ. Responsive Web Design) з використанням медіазапитів @media. Адаптивний веб-дизайн автоматично підлаштовується під різні розміри екранів та області перегляду[5]. На екранах з невеликою роздільною здатністю головне меню показує по одній картці рецепту в ряд.

## Логотип
Формування візуального образу веб-додатка починається з його шапки, головним елементом якої є логотип ресурсу. Для забезпечення унікальності проєкту та його впізнаваності, логотип був розроблений мною самостійно. Він органічно поєднує в собі затверджену кольорову гаму та стилістику проєкту. Розміщення логотипа у лівому верхньому куті сторінки відповідає класичним паттернам користувацького дизайну і слугує зручним навігаційним елементом для повернення на головну сторінку.
